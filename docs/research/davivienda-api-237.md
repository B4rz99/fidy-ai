# Davivienda API 237: production-readiness investigation

Research date: 2026-08-22

Scope: Davivienda API 237, authenticated laboratory portal and downloaded laboratory materials, with an official Bancolombia Account Information comparison baseline.
Repository context: Fidy terminology and gates from [`CONTEXT.md`](../../CONTEXT.md), [system architecture](../../ARCHITECTURE.md), [server architecture](../../apps/server/ARCHITECTURE.md), and [`CODING_STANDARDS.md`](../../CODING_STANDARDS.md).

## 1. Executive verdict

### Final classification

**The reviewed laboratory contract supports interactive access only; unattended automatic Synchronization and production support are not established.**

API 237 documents Account discovery, balances, and account movements in a laboratory environment. It also documents a bank-hosted authentication widget and a bearer access token with a 15-minute lifetime (900 seconds in the flow diagram). The reviewed Davivienda materials do not document a refresh token, durable data consent, consent identifier, consent lifecycle, revocation operation, unattended renewal, or a production API 237 contract. Therefore Fidy cannot safely implement its required automatic Synchronization after the initial User authorization. This conclusion is based on the documented authorization contract, not on the fact that a movement endpoint exists. [D-PORTAL] [D-GUIDE p. 11] [D-FLOW p. 1] [F-CONTEXT] [inference]

The laboratory surface is technically useful for a bounded proof of concept, but it is not enough to make Davivienda a SupportedInstitution. Production availability, production commercial eligibility, exhaustive history traversal, movement completion semantics, and durable continuation remain unproven. The correct Fidy posture is to retain email ingestion as a fallback, keep Davivienda disabled behind the SupportedInstitution gate, run the approved laboratory spike when credentials can be handled safely, and obtain written Davivienda confirmation before production enablement. [D-TERMS pp. 1, 3] [D-FAQ] [F-CONTEXT] [inference]

### What was proven

- The authenticated portal exposes API product 237 as Open Banking / Agregación Bancaria and exposes an OAS3 contract version 0.0.1. [D-PORTAL]
- The OAS exposes four read operations: account discovery, aggregate balances, one-account balances, and one-account transactions. [D-OAS lines 1-9, 221-230, 435-444, 656-717]
- The transaction schema has a generated transaction identifier, debit/credit direction, value date, amount, currency, and a four-character status field whose example is STLD. [D-OAS lines 1078-1094, 1113-1183]
- The downloaded authentication guide and flow use a bank-hosted widget and return a bearer token with a 15-minute lifetime; the flow explicitly shows response_type=token and expires_in=900. [D-GUIDE pp. 6-7, 11] [D-FLOW p. 1]
- Davivienda’s public laboratory FAQ gives a maximum of 100 API consumptions per hour and a 60-second API timeout, but does not define the rate-limit scope or a Synchronization polling contract. [D-FAQ]
- Davivienda’s portal terms require a separate production process, legal/technical/operational documents, commercial accompaniment, and a production certificate generated by the user through a certification authority. [D-TERMS pp. 1, 3-5]
- Bancolombia’s official baseline documents an Account Access Consent resource, ConsentId, consent status, permission scopes, authorization-code flow, refresh token, mTLS, private_key_jwt, PAR, PKCE S256, and a declared transaction page size of up to 40 movements. [B-AI lines 19-39, 78-119, 123-157] [B-AUTH lines 18-63] [B-TRANSACTIONS lines 82-110, 660-744]

### What failed Fidy’s gate

Durable unattended access fails on current evidence. Exhaustive traversal, conclusive completed-movement semantics, stable repeated movement identity, freshness/coverage observability, revocation behavior, production eligibility, and retention/deletion obligations are either absent from the reviewed Davivienda contract or require written confirmation. [D-OAS lines 1050-1077, 1113-1183] [D-FLOW p. 1] [F-CONTEXT] [inference]

## 2. Research method and evidence classes

### Method

1. Read the Fidy repository documents before evaluating the product.
2. Inspected the authenticated API 237 page in the existing Helium tab without closing it. The restored authenticated tab was left on the API 237 document and was not navigated after the user requested that it remain dedicated to inspection.
3. Read the raw OAS linked by the portal in a separate tab and retained the downloaded file in Downloads only.
4. Inspected the four downloaded Davivienda complementary materials in Downloads. No gated document was copied into the repository.
5. Used official Davivienda public FAQ, terms, contact, product, and Open Finance pages for production/commercial context.
6. Navigated the Bancolombia public portal in a separate Helium tab, used its documentation controls, and inspected the official downloaded specifications and official support/legal materials. Direct static specification URLs returned a portal-header-dependent error when opened without the portal context; this was not treated as product unavailability.
7. Did not create or modify an application, subscription, certificate, production access, or real-customer authorization. No live bank data was queried.

### Evidence classes

- **Portal fact:** text, links, product metadata, or section structure visible in the authenticated or public portal.
- **Downloaded-document fact:** text or schema in a downloaded official file; the report gives filename and page/line references, but does not republish the gated files.
- **Sandbox observation:** a result obtained by safely invoking a laboratory endpoint or UI. No live endpoint invocation was completed in this investigation.
- **Inference:** a conclusion derived from one or more facts. Inferences are labeled explicitly and never treated as production contract.
- **Unknown:** the reviewed sources do not establish the fact. Unknown is not evidence of absence in production.

### Fidy decision criteria applied

Fidy defines an Account as an institution-held account authorized through a Connection; removing authorization stops future Synchronization without ordinary Connection lifecycle changes deleting prior Transactions that retain a valid purpose. A SupportedInstitution requires production eligibility, secure durable authorization, Account and completed-movement semantics, stable traversal, observable coverage/freshness, and revocation/deletion obligations. Synchronization means retrieving maximum available authorized Account, Balance, and movement data and keeping it current when the institution permits. [F-CONTEXT]

Fidy’s Transaction is only a completed movement of Money. Pending, rejected, cancelled, and provisional institution movements are not Transactions. Fidy’s FinancialRecord is coherent and best-available, exposes uncertainty, and never claims to be complete or authoritative; SourceAttestation explains where each Transaction was learned while the evidence remains validly retained. [F-CONTEXT]

## 5. Authorization and consent

### Exact documented flow

The Davivienda flow is a token/implicit-style flow rather than a documented authorization-code flow:

1. The third party calls GET /oauth2-provider/type2/v1/authorize with response_type=token and scope=review.
2. Davivienda returns a 302 URL for the Web Authenticator at a Davivienda labs host.
3. The customer authenticates in the bank-hosted widget.
4. Davivienda redirects to the third party with rstate, confirmation, and username.
5. The third party calls the authorize resource again, adding redirect_uri and those returned parameters.
6. Davivienda redirects to the third party with an access token in the URL fragment, expires_in=900, scope=review, and token_type=bearer.

This sequence is shown in the downloaded flow diagram. The guide separately describes the second OAuth Web Authentication call as generating the token and states that it is valid for 15 minutes, with the source’s own typo “900ms”. The flow’s expires_in=900 resolves the intended unit as 900 seconds. [D-FLOW p. 1; D-GUIDE p. 11]

### Consent, account selection, and revocation

The flow includes a consented_on timestamp in the token fragment, but the reviewed Davivienda materials do not define a Consent object, ConsentId, purpose field, duration, status lifecycle, consent query operation, or revocation operation. A token timestamp is not a durable consent contract. [D-FLOW p. 1]; [D-OAS lines 1-5, 7-9, 221-230, 435-444, 656-717]; [inference]

The guide says that Accounts lists the accounts of the authenticated user and that specific balances/transactions use AccountIdentification obtained from a previous API. It does not say whether the User selects individual Accounts in the bank UI, whether all eligible deposit accounts are authorized, or how account selection changes later. [D-GUIDE pp. 13-17]; [D-OAS lines 7-9, 435-472, 656-717]

The OAS documents an expired-token response (“Access token has Expired”) and generic authentication errors, but no revocation endpoint or revocation-specific response. Davivienda portal terms allow Davivienda to block, cancel, or revoke portal credentials/services in specified circumstances; that is not a documented User data-consent revocation lifecycle for API 237. [D-OAS lines 69-106]; [D-TERMS pp. 6-8]; [inference]

### Central authorization answer

**No. Current evidence does not establish that Fidy can continue Synchronization automatically after initial bank authorization.** The documented token expires after 900 seconds, and no unattended renewal or durable consent mechanism is documented. Requiring the User to repeat the bank-hosted authentication after expiry would be interactive access only and would fail Fidy’s automatic Synchronization requirement. [D-GUIDE p. 11]; [D-FLOW p. 1]; [F-CONTEXT] [inference]

## 6. Accounts

### Operations and schema

API 237 exposes:

- GET /open-banking/v1/accounts: “Devuelve la información básica de las cuentas de depósito que el usuario final ha autorizado a acceder”.
- GET /open-banking/v1/balances: balances for previously authorized deposit accounts.
- GET /open-banking/v1/accounts/{AccountIdentification}/balances: balance for one previously authorized deposit account.
- GET /open-banking/v1/accounts/{AccountIdentification}/transactions: movements for one previously authorized deposit account.

The account operation requires Bearer Authorization, x-fapi-interaction-id, Accept, and Content-Type; x-fapi-auth-date and x-fapi-customer-ip-address are optional. [D-OAS lines 7-49, 221-230, 435-484, 656-717]

AccountReportItem requires AccountIdentification, AccountName, AccountType, AccountReference, and AccountStatus. AccountIdentification is described as a unique account identifier; AccountReference is the last four digits; AccountStatus is the current account status. AccountType is a four-character string without a contractual dictionary. [D-OAS lines 909-947]

The downloaded sandbox scenario includes a savings-account example and COP, but that is laboratory sample evidence, not a production product coverage promise. The API description is generic to deposit accounts. [D-SCENARIOS p. 1]; [D-OAS lines 1-5, 909-947]

## 7. Balances

API 237 provides aggregate and per-account balance operations. BalanceItem requires AccountIdentification, AccountName, AccountType, AccountReference, AccountStatus, and MultilateralBalance. MultilateralBalance contains Amount, Currency, and Type; Amount is numeric and described as two decimals, Currency is three characters with COP as the example, and Type has AVLB as the example. [D-OAS lines 221-230, 435-503, 982-1049]

The OAS does not define:

- a balance as-of timestamp;
- a freshness timestamp;
- current versus ledger balance semantics;
- pending amount semantics;
- credit limits;
- liabilities;
- a complete balance-type dictionary beyond the AVLB example; or
- a numeric precision contract tied to Fidy Currency beyond the two-decimal description.

Therefore Fidy can retain the raw balance response as an unclassified provider observation, but cannot yet map AVLB to a complete Fidy balance semantic or claim observable freshness. [D-OAS lines 1026-1049] [inference]

## 8. Movements and status semantics

### Operation and fields

The transaction operation is GET /open-banking/v1/accounts/{AccountIdentification}/transactions. FromValueDate and ToValueDate are optional and use YYYY-MM-DD. If omitted, the OAS says the response starts at the first authorized transaction and ends at the last authorized transaction. [D-OAS lines 656-717]

TransactionReportItem requires:

- TransactionIdentification;
- TransactionInformation;
- CreditDebitIndicator;
- ValueDateTime; and
- InstructedAmount.

It also exposes TransactionReference, RequestedExecutionDate, CreditorAgent, Status, and creditor information. TransactionIdentification is described as “Identificador único generado para la transacción”. CreditDebitIndicator is DBIT or CRDT. ValueDateTime is the application date/time. Status is a four-character string with STLD as the example. [D-OAS lines 1113-1198]

### Fidy completion decision

The OAS does not define a complete status dictionary or state transitions. It gives STLD as an example but does not define that code’s contractual meaning. It does not document pending, rejected, cancelled, reversed, corrected, or provisional semantics, nor reversal/correction references. It also does not say whether a supposedly completed movement can later change status. [D-OAS lines 1176-1183] [D-SCENARIOS p. 1]

Accordingly, Fidy must not turn every returned movement into a Transaction. Until Davivienda supplies the status dictionary and Correction/Reversal rules, all statuses—including STLD—remain institution observations rather than conclusively completed Fidy Transactions. This is a deliberate application of Fidy’s “completed movement only” rule. [F-CONTEXT] [inference]

### Identity and repeatability

The schema’s description of TransactionIdentification as unique is positive evidence for a candidate stable movement key. It is not proof that the identifier remains stable across repeated calls, pages, date ranges, reauthorization, or production migration. No live repeated retrieval was run, so repeated-call stability is unobserved. [D-OAS lines 1122-1127] [sandbox observation: not run]

## 9. History and pagination

### Davivienda contract

Davivienda documents FromValueDate and ToValueDate. If omitted, the OAS says the first and last authorized transactions are used. It does not state the maximum lookback in days/months, a default page size, a page-size limit, a page-number parameter, a cursor parameter, an ordering guarantee, a snapshot boundary, or a delta token. [D-OAS lines 706-717]

The generic Links schema says it contains pagination links and that an absent Next means the last page; it also defines Previous, Last, and Self. However, the transactions operation does not define how pages are requested, how link traversal is made consistent while postings change, or how a consumer distinguishes an exhausted result from a malformed/missing link. The generic schema is not enough to establish exhaustive traversal for Fidy. [D-OAS lines 1050-1077] [inference]

No incremental synchronization/delta-feed operation is documented. No concurrent-posting consistency rule or ordering guarantee is documented. Repeated traversal and oldest-available movement were not tested. [D-OAS lines 656-717] [sandbox observation: not run]

### Deterministic-exhaustion result

**Not established.** Fidy cannot claim maximum available history or reliable exhaustive pagination for API 237 from the reviewed contract. The initial request can omit dates, but “first authorized transaction” is not a maximum-history guarantee unless the date horizon, ordering, page mechanics, and terminal condition are contractually defined. [D-OAS lines 706-717, 1050-1077] [inference]

## 14. Bancolombia baseline

### Product and account-information scope

The Bancolombia public portal product page for Account Information shows API Public, version 1.0.0, Sandbox Gratis, and a Producción contact path. The official product documentation explains that an AISP creates an account-access-consent resource and receives ConsentId; the consent contains permissions, expiration, and a transaction history range. ### Consent and authorization

Bancolombia’s official authorization documentation describes:

- OIDC discovery for authorization-server configuration;

- PKCE code_verifier/code_challenge;
- bank-controlled customer redirection/authentication;

The Accounts schema requires AccountIdentification, AccountReference, AccountStatus, and AccountType, with AccountName optional. The Transactions schema documents:

- fromValueDate and toValueDate;
- a maximum query range of four months in the YAML;
- pageNumber;
- up to 40 movements per page when more than 40 records exist;
- Previous/Self/Next/Last pagination links;
- TransactionIdentification described as unique;
- BookingDateTime;
- ValueDateTime;
- DBIT/CRDT direction;
- COP/USD amount fields; and

[B-TRANSACTIONS lines 42-110, 660-744, 763-807, 1099-1134]

The official 2025 external-API regulation imposes technical/security, data-protection, incident, audit, commercial, and termination obligations. It requires secure transport and encryption, qualified digital certificates, security standards, and in some open-finance cases PCI-DSS with QSA/AoC if card data is stored, processed, or transmitted. The regulation says monetization is defined according to the contracted service, so the public materials do not provide a universal price. It requires a contract and a production pilot, permits limits or suspension, provides a support scheme, and allows audit/inspection of risk, continuity, security, compliance, and process controls. [B-REG pp. 4-6, 10, 18-22]

## 17. Conflicting evidence

1. **900ms versus 15 minutes:** The guide says 15 minutes and then contains “900ms”; the flow diagram says expires_in=900. The flow resolves this as 900 seconds, not milliseconds. [D-GUIDE p. 11]; [D-FLOW p. 1]
2. **consented_on versus no Consent object:** The flow includes consented_on in the token fragment, but no ConsentId, consent resource, duration, status, or revocation operation is defined. A timestamp is not a durable consent lifecycle. [D-FLOW p. 1]; [D-OAS]; [inference]

The generic link cannot prove deterministic exhaustive traversal. [D-OAS lines 1050-1077] [inference]
4. **Laboratory identity versus production evidence:** The Davivienda terms say the laboratory is intended to emulate production, but also describe separate production infrastructure, a separate certificate, and a separate legal/technical/operational process. That does not prove a current API 237 production contract. [D-TERMS pp. 1, 3]
5. **Portal access restriction versus product availability:** The authenticated session returned access denied for the control-panel/catalog routes during inspection, while API 237 itself remained visible. This is a session/portal observation, not evidence that the product is archived or unavailable. [D-PORTAL]; authenticated portal inspection.
6. **Bancolombia history window:** official Markdown says 90 days when From is omitted; a technical error table says maximum 3 months; the transaction YAML says max 4 months. This baseline needs clarification before treating history as deterministic. [B-AI lines 92-97, 151-157]; [B-TRANSACTIONS lines 42-81]
7. **Bancolombia account-type code:** the schema dictionary says CAAC for current account, while a response example contains CACC. The schema and observed example need reconciliation. [B-ACCOUNTS lines 138-152, 447-456]
8. **Bancolombia authorization declarations:** the authorization prose describes authorization code for product resources, while the downloaded Accounts, Balances, and Transactions OAS files declare `OAuthProvider-ClientCredentialsFlow` on those operations. ## Summary

- **What was proven:** Davivienda API 237 is a laboratory-labeled Open Banking/Agregación Bancaria product with account, balance, and movement read shapes, a bank-hosted widget, and a 15-minute bearer token.
- **What failed:** The reviewed Davivienda materials do not establish durable unattended access, refresh, durable consent, revocation, exhaustive pagination, conclusive completion statuses, observable coverage/freshness, or production readiness.
- **What remains unknown:** Current production API 237 availability, production contract/version/base URL, eligibility, commercial terms, consent lifecycle, account selection, status dictionary, history limits, pagination consistency, freshness, and data obligations.
- **What requires written Davivienda confirmation:** All unresolved production, authorization, data semantics, continuation, commercial, security, retention, and deletion questions in Section 18.
- **SupportedInstitution result:** Davivienda does not pass Fidy’s SupportedInstitution gate.
- **Next technical action:** Run the approved bounded, redacted laboratory spike when credentials and certificate material are safely available, while obtaining the current production/OAuth/consent contract in parallel; laboratory success cannot enable Davivienda.
- **Next commercial action:** Contact Davivienda’s commercial/support path for production eligibility, pricing, SLA, security/privacy annexes, retention/deletion rules, and onboarding terms.
- **Final classification:** **The reviewed laboratory contract supports interactive access only; unattended automatic Synchronization and production support are not established.**
