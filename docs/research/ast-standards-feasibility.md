# Which modelling rules are enforceable?

Research at `1bbd8d3103` (branch `research/ast-standards-feasibility`). Scope: the previously proposed first-party-interface, first-party-class-inheritance, and readonly-array-return checks, plus the proposed `Record<string, unknown>` change and [`dmmulroy/anti-slop`](https://github.com/dmmulroy/anti-slop/tree/c44ef22ca116d0ba62a3ff663a0bd13a3f3fa40b). This is an assessment, not a new gate. **Enforceable** below means a precisely stated _syntactic or symbol-resolvable subset_, not proof that the design is sound.

## Short answer: `Record<string>` is not a TypeScript type

[`Record<Keys, Type>`](https://www.typescriptlang.org/docs/handbook/utility-types.html#recordkeys-type) requires both a key type and a value type. The repository's isolated TypeScript compiler reports `TS2314: Generic type 'Record' requires 2 type argument(s)` for `type R = Record<string>;`. If the intended value type is `string`, the spelling is `Record<string, string>`, **not** a substitute for unknown values. If the fields are known, use their schema-derived/named shape. If they genuinely are not, `unknown` describes the boundary honestly; decode before trusted use rather than inventing a value contract. This is also the explicit difference between _core_ and _shell_ policy in [CODING_STANDARDS.md:96–106](../../CODING_STANDARDS.md#L96-L106) and the trust-boundary requirement in [SECURITY_STANDARDS.md, §4](../../SECURITY_STANDARDS.md#4-validation-injection-and-safe-output).

Concrete shell examples: [category query: `sql.unsafe<Record<string, unknown>>`](../../apps/server/src/shell/categories/list-categories.ts#L17-L26) hands its result to [a `rows: unknown` decoder](../../apps/server/src/shell/categories/query.ts#L22-L31); [PAT listing](../../apps/server/src/shell/tokens/list-pats.ts#L76-L106) decodes the result with a row schema. [Hosted structured generation](../../apps/server/src/shell/hosted-inference/contract.ts#L89-L100) uses `Encoded extends Readonly<Record<string, unknown>>` as a structural _generic bound_, not a value returned to callers as an open dictionary. A rule that indiscriminately removes those spellings either rejects honest boundary types or incentivizes made-up types. Whether a particular SQL API can accept an even less specific `unknown` is a separate API review, not a replacement with `Record<string>`.

## What anti-slop would actually do

The inspected upstream snapshot is [commit `c44ef22…`](https://github.com/dmmulroy/anti-slop/tree/c44ef22ca116d0ba62a3ff663a0bd13a3f3fa40b); its package declares [`private: true`, version `0.1.2`, TypeScript `7.0.2`, and `@oxlint/plugins`/Oxlint `1.78.0`](https://github.com/dmmulroy/anti-slop/blob/c44ef22ca116d0ba62a3ff663a0bd13a3f3fa40b/package.json#L1-L45). Fidy currently uses Oxlint `1.83.0` with a [local JavaScript plugin](../../.oxlintrc.json#L1-L9); the inspected package is **not a published drop-in dependency** at this snapshot. Compatibility and how to load its TypeScript entrypoint would need a separate test before adoption.

Its [`no-unsafe-dictionary-type` implementation](https://github.com/dmmulroy/anti-slop/blob/c44ef22ca116d0ba62a3ff663a0bd13a3f3fa40b/src/rules/no-unsafe-dictionary-type.ts#L77-L137) rejects dictionary contracts with a direct value type of `unknown`, `any`, `object`, `{}`, or unsafe aliases/unions; it does **not** permit `Record<string>` as a shorthand. [Tests](https://github.com/dmmulroy/anti-slop/blob/c44ef22ca116d0ba62a3ff663a0bd13a3f3fa40b/src/rules/no-unsafe-dictionary-type.test.ts#L7-L115) deliberately allow concrete dictionary values, nested `unknown` fields, `Map<string, unknown>`, a locally shadowed `Record`, and **generic constraints** `T extends Record<string, unknown>`; they reject open dictionary values, wrappers, mapped/index signatures, and aliases. The [classifier](https://github.com/dmmulroy/anti-slop/blob/c44ef22ca116d0ba62a3ff663a0bd13a3f3fa40b/src/shared/dictionary-types.ts#L220-L273) checks the _value_ argument; do not mistake it for a proof of finite keyspace, trusted source, or schema decoding. As AST-local lexical analysis it also cannot establish arbitrary types imported from other modules.

Fidy already has [its own dictionary rule](../../scripts/oxlint/effect-guards.js#L758-L800), [enabled only in core](../../.oxlintrc.json#L329-L340), with [negative and shadowed-`Record` probes](../../apps/server/scripts/check-lint-guards.ts#L56-L80). It also rejects generic constraints: a temporary core probe containing `type Bound<V extends Readonly<Record<string, unknown>>> = V` and `type Finite = Record<"open" | "closed", unknown>` produced **two** `effect-guards(no-unsafe-dictionary-type)` errors under the real Oxlint config. Upstream explicitly allows the first case ([test lines 39–42](https://github.com/dmmulroy/anti-slop/blob/c44ef22ca116d0ba62a3ff663a0bd13a3f3fa40b/src/rules/no-unsafe-dictionary-type.test.ts#L39-L42)); neither is a license to weaken existing core policy without review. An all-repository adoption would additionally encounter the shell SQL/boundary types above and [test input builders](../../apps/server/cloudflare/ingestion/statement-ingestion.test.ts#L559-L568). **Recommendation:** keep the existing scoped gate; review individual known-shape shell/test returns on their merits. Do not install a duplicate broad plugin just to ban the text `Record<string, unknown>`.

## Candidate 1 — ordinary first-party interfaces

**Already largely enforced.** [CODING_STANDARDS.md:76–81](../../CODING_STANDARDS.md#L76-L81) permits `interface` for deliberate declaration merging/module augmentation. [`.oxlintrc.json:114`](../../.oxlintrc.json#L114) already enables Oxlint's [`typescript/consistent-type-definitions: ["error", "type"]`](https://oxc.rs/docs/guide/usage/linter/rules/typescript/consistent-type-definitions). Its [route-file override](../../.oxlintrc.json#L258-L264) disables the rule throughout `apps/web/src/app/routes.ts` because that file has a [necessary `declare module "@tanstack/react-router" { interface Register … }`](../../apps/web/src/app/routes.ts#L143-L148). A direct Oxlint probe with the built-in rule enabled reports that _very_ `Register` as a violation; TypeScript's [module-augmentation semantics](https://www.typescriptlang.org/docs/handbook/declaration-merging.html#module-augmentation) explain why switching it to `type` is not equivalent.

**Precisely enforceable subset:** reject `TSInterfaceDeclaration` in first-party source unless it is in a deliberate `declare module "…"` or `declare global` augmentation; for the currently known exception additionally require module name `@tanstack/react-router`, name `Register`, and route-file location. AST ancestry is sufficient to recognize this syntax, but `namespace X { interface Y }` is _not_ automatically an allowed module augmentation; neither a comment nor being in a `.d.ts` file proves the exception is justified. Test: ordinary interface in that same route file **fails**, the existing `Register` **passes**, one newly added ordinary interface elsewhere **fails**. A narrow guard on the exempt file alongside the existing built-in rule closes the actual hole; alternatively replace the built-in with an exception-aware rule and test equivalent coverage across all first-party files. A blanket new interface rule would duplicate existing enforcement, while removing the override without replacing it breaks the framework contract. Even a precise gate proves only the declaration's _syntax_, not that merging was necessary.

## Candidate 2 — extending a first-party class

[CODING_STANDARDS.md:157–168](../../CODING_STANDARDS.md#L157-L168) says first-party classes should express Effect errors/services, not shared behavioural inheritance; it currently claims no linter can draw the line. That is too absolute. An AST **alone** can flag `class X extends B`, but cannot determine whether `B` is locally authored, imported, re-exported, aliased, or supplied by a vendor. The [TypeScript compiler API](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API) exposes `getSymbolAtLocation`, declaration origins, and type information: in an isolated compiler fixture, a direct base imported through a re-export resolved back to the local class, an external base resolved to its vendor `.d.ts`, and `class X extends localFactory()` had no direct symbol but its constructor return type resolved to the local class. **Thus direct symbol-resolvable first-party inheritance is enforceable** with a project-aware checker (or an Oxlint typed API proved to provide equivalent resolution).

**Not a complete design proof:** constructors supplied by arbitrary factories, generic higher-order classes, missing/`any` types, path aliases/project references, and re-exports can be ambiguous. The current two-project AST inventory (production `apps/server/src` and `apps/web/src`, excluding tests/`.d.ts`) has **141 `extends` declarations but no direct identifier base**: 64 `Schema.Error(…)`, 55 `Data.TaggedError(…)`, 13 `Context.Service(…)`, five `HttpApi.make(…)`, three `HttpApiMiddleware.Service(…)`, and one `OrdinaryFidyApi.add(…)`. With the installed isolated classic compiler, only **13/141** constructor-return declarations resolved, all in `effect` definitions; treating every unresolved factory as a violation would break legitimate production classes. An implementable **narrow** gate would reject a base whose symbol/constructor type **positively resolves** to a first-party class and test local direct/imported/re-exported/factory positives versus vendor and Effect negatives; report unresolved bases for review or limit those to explicitly tested allowed factory forms. Do not advertise that check as establishing “classes only where an Effect API asks for one”: whether a class models behaviour and whether a factory is appropriate remain design-review decisions. A restrictive new whitelist is possible but has real maintenance cost; no present direct violation justifies it urgently.

## Candidate 3 — readonly arrays in return types

[CODING_STANDARDS.md:120–135](../../CODING_STANDARDS.md#L120-L135) explicitly requires `ReadonlyArray<T>` in returns and says parameters, **not returns**, are currently enforced in core. TypeScript's [readonly-array documentation](https://www.typescriptlang.org/docs/handbook/2/objects.html#the-readonlyarray-type) states that `readonly T[]` is equivalent spelling and that a mutable array can be passed/assigned to a readonly view, but the reverse assignment is prohibited. Oxlint's [`typescript/array-type`](https://oxc.rs/docs/guide/usage/linter/rules/typescript/array-type) only chooses **spelling**, not mutable versus readonly. [`prefer-readonly-parameter-types`](https://oxc.rs/docs/guide/usage/linter/rules/typescript/prefer-readonly-parameter-types) concerns inputs, not outputs.

**Precisely enforceable subset:** at first-party exported core function/arrow return annotations, reject top-level `Array<T>` and `T[]`; permit `ReadonlyArray<T>` and `readonly T[]`. Add negatives for both spellings and positive readonly counterparts; handle public methods and re-exports explicitly if they belong to the contract. This is only a lexical guard: `type Mutable = T[]; f(): Mutable`, an inferred export, `Effect.Effect<T[]>`, `Promise<T[]>`, property/indexed-access return aliases, and wrapped/nested arrays can escape it. A type-aware rule could inspect resolved return _and_ its relevant success container(s), but must define public API ownership and avoid banning private local accumulators, callbacks, and mutable arrays received internally. `ReadonlyArray` does not freeze elements or runtime arrays, nor does checking annotations prove a boundary cannot leak a mutable alias.

**Measured value now:** an AST walk over non-test core sources found 87 directly exported function/arrow declarations (85 explicit return annotations); none had an explicit top-level mutable array return. Of 357 core function-like nodes including callbacks/helpers, four inferred mutable-array return types were internal, not evidence of a broken exported contract. Thus the narrow syntax gate is feasible and cheap but initially a future-regression check with zero existing positives; a broad checker that reports all four is **wrongly scoped**. Defer type-aware wrappers until positive/negative tests demonstrate a real escape worth guarding; keep semantic API ownership in review.

## Other attractive-looking rules: decision boundary

| Standard                                                          | Reliable machine predicate                                                                                                                                                                                                 | What it cannot establish                                                                                                                                                                               |
| ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Finite `Record` vs open unknown-value dictionary                  | AST/value-type rule **already** gates core ([config](../../.oxlintrc.json#L329-L340)); a broader gate must enumerate legitimate shell inputs.                                                                              | Whether data is genuinely open or was decoded before trusted use ([standards](../../CODING_STANDARDS.md#L96-L118); [security §4](../../SECURITY_STANDARDS.md#4-validation-injection-and-safe-output)). |
| Tuple shape vs named object; paired optionals as a union          | Flag syntax such as tuple types or two optional properties ([standards](../../CODING_STANDARDS.md#L55-L95)).                                                                                                               | Whether positions are genuinely unnamed; whether two fields co-occur as a business invariant. A global ban would reject legitimate interop/row/Effect tuples.                                          |
| No duplicate cross-application contracts                          | Import/dependency fences and generated-artifact checks cover concrete wiring ([ARCHITECTURE.md:20–44](../../ARCHITECTURE.md#L20-L44)).                                                                                     | Whether two hand-maintained types _mean_ the same operation or diverge semantically.                                                                                                                   |
| Useful comments, lawful error handling, proof of runtime decoding | A gate can recognize particular forbidden APIs or verify a named negative test exists ([standards](../../CODING_STANDARDS.md#L30-L52); [security §4](../../SECURITY_STANDARDS.md#4-validation-injection-and-safe-output)). | Whether a comment explains the hard part, `orDie` denotes a defect, or a test establishes fail-closed behaviour. Keep design/security/spec review.                                                     |

## Recommendation and unresolved questions

1. **First experiment:** tighten the _already-existing_ interface rule's route-file exception with a narrow, tested AST guard; do not announce it as a new repo-wide interface ban.
2. If inheritance regressions appear, prototype a **type-aware positive-resolution check** with direct, re-export, factory, vendor, and unresolved tests. Update the “no linter could draw” wording only to the subset actually guaranteed; retain review for class purpose.
3. A scoped return-annotation array guard is feasible but lower priority: measure future violations and define export/method/wrapper scope before asserting stronger guarantees.
4. Do not replace `Record<string, unknown>` with invalid `Record<string>` or enforce a repo-wide anti-slop dictionary ban. Keep genuinely untrusted/open boundary values honest and decode them.

**Unresolved:** Should the current core dictionary rule deliberately exempt pure generic constraints and/or finite `Record` keyspaces, as upstream does for the former? Does the project want to recognize inferred/wrapped _exported_ array returns, and if so which Effect/Promise/container contracts count? These are policy decisions; neither requires weakening runtime validation.
