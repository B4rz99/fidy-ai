# BillingAttempt collection lifecycle (#711)

Subscription owns the BillingAttempt and its checkout reference. One authenticated payment action creates one retry-stable BillingAttempt and one armed mutation. D1 is the authority for both collection admission and settlement; Workflow history is not. A Wompi transaction ID or signed callback is a lookup hint, never settlement or authorization to collect.

## Independent facts

- **Attempt outcome:** `pending` → `failed` only after verified negatives and the Wompi retry opportunity; `pending` or `failed` → `succeeded` on matching, finalized, provider-GET-verified approval. `succeeded` never regresses. A negative is provisional: it never proves that no charge can later be approved.
- **Collection arm:** `armed` → `sent` is committed _before_ the sole POST. A sent arm never returns to `armed`. A lost POST response, interrupted Workflow, missing ID, or provider outage cannot justify another POST.
- **User-level admission:** an existing attempt that is not succeeded blocks a _different_ payment action for that User until an attributable provider no-charge confirmation is durably recorded. The same PaymentRequestId remains idempotent and returns its existing BillingAttempt. A verified negative alone, timeout, failed lookup, browser redirect, or exhausted retry budget cannot lift the block. A succeeded attempt does not block a separate, newly authorized action.
- **Recovery:** a signed event or an operator-confirmed transaction ID starts or renews a bounded provider GET, not a POST. Exhausted lookups require a new authenticated event or a privileged renewal with Wompi's confirmed ID. If Wompi cannot establish an ID or confirm no charge, the User remains blocked. A no-charge confirmation must name the exact User, BillingAttempt, reference, provider environment, support case, operator, and instant; it is not provider-GET settlement evidence. A later verified approval still wins, and its atomic settlement records a recovery-review intent for human investigation of any newly collected charge/refund.

## Transition table

| Input                                              | Preconditions and evidence                                                      | D1 outcome                                                                                                  | User admission                                    |
| -------------------------------------------------- | ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| New payment action                                 | Authenticated User, new PaymentRequestId, no outstanding un-cleared attempt     | Create BillingAttempt, arm, outbox atomically                                                               | Block a different action                          |
| Repeat payment action                              | Same User and PaymentRequestId                                                  | Return same BillingAttempt, never a new arm                                                                 | Unchanged                                         |
| Workflow collection                                | Arm still `armed`                                                               | Atomically mark `sent`, then make one POST outside D1                                                       | Blocked until resolution                          |
| Lost POST response / no ID                         | Sent arm                                                                        | No settlement, no rearm; await callback or operator                                                         | Blocked                                           |
| Signed callback / returned or support-confirmed ID | Authentic hint; no settlement facts accepted from it                            | Store bounded lookup intent                                                                                 | Unchanged                                         |
| GET unavailable, malformed or mismatched facts     | No verified snapshot                                                            | Retry within budget or await privileged recovery; no settlement                                             | Unchanged                                         |
| Matching verified pending/negative                 | Complete captured reference, environment, Money and optional source match       | Append verified evidence; fail only after retry opportunity, never after approval                           | Still blocked                                     |
| Matching verified approval                         | Same captured facts and finalized instant, even after failure                   | Atomically record evidence, success, paid period, Subscription, audit and follow-up intent                  | A new action may be authorized                    |
| No-charge confirmation                             | Privileged, attributable Wompi support evidence bound to a sent arm; no success | Record clearance without changing the attempt's verified outcome                                            | Unblock; keep late-approval reconciliation active |
| Replay / reordered callback                        | Same signed event, or older event after approval                                | No extra POST, settlement, or unbounded lookup; newer signed approval with the same second remains eligible | Unchanged                                         |

**Cross-User invariant:** a provider ID, callback, or URL never selects a User. Provider GET facts must match the stored attempt before any write to evidence, Subscription, audit or follow-up intent. The checkout admission guard and the settlement update both run in D1, not in process-local state. Duplicate and concurrent requests see one atomic ordering.

**Operational limit:** Wompi documents charge lookup by transaction ID. When no ID or definitive no-charge confirmation can be obtained, automated reconciliation cannot infer an outcome from a merchant reference. Leave the sent arm and User block intact and escalate; never manufacture certainty from a timeout.
