# Effect v4 unstable RPC

Project baseline: `effect@4.0.0-rc.112`; source checkout `.repos/effect` at `f239b5b6cc`.

Use this pattern for `effect/unstable/rpc`. RPC is an internal, typed Effect-to-Effect protocol. It is not the public HTTP API contract: define public operations with HttpApi, and use RPC only behind internal transports or Cluster entities.

## Boundary decision

| Need                                                                     | Boundary                                             |
| ------------------------------------------------------------------------ | ---------------------------------------------------- |
| Browser or third-party public API, OpenAPI, HTTP status/header semantics | HttpApi                                              |
| Internal typed request/response or stream over an Effect transport       | RPC                                                  |
| Addressed, sharded, durable in-process/distributed behavior              | Cluster `Entity`, whose protocol is an `RpcGroup`    |
| Durable multi-step orchestration                                         | Workflow, even when Cluster RPC carries its commands |

Do not expose an RPC transport as the product's public API merely because it is easy to derive a client. RPC wire compatibility, transport behavior, and unstable APIs remain internal concerns.

## Define the protocol once

An RPC definition owns the request tag, payload schema, success schema, declared error schema, optional defect schema, middleware, annotations, and streaming flag. `Rpc.make` derives its key from the tag; `RpcGroup.make` indexes definitions by that key (`.repos/effect/packages/effect/src/unstable/rpc/Rpc.ts:902-956`, `.repos/effect/packages/effect/src/unstable/rpc/RpcGroup.ts:402-416`).

```ts
import { Schema } from "effect";
import { Rpc, RpcGroup } from "effect/unstable/rpc";

const GetTurn = Rpc.make("GetTurn", {
  payload: { turnId: TurnId },
  success: Turn,
  error: TurnNotFound,
});

export const AgentProtocol = RpcGroup.make(GetTurn);
```

Rules:

- Give every operation a stable, globally comprehensible tag. A rename is a wire-protocol change.
- Put all untrusted payload, success, and expected failure values behind schemas. Do not use `Schema.Unknown` to avoid modeling a boundary.
- Export named RPC definitions or the owning group/entity; do not duplicate payload types by hand—derive them with `Rpc.Payload` and `Rpc.ExtractTag` when needed.
- Compose a cohesive protocol with `RpcGroup.make`, `add`, or `merge`. Use `prefix` only as a deliberate namespace migration, because it changes RPC tags and keys.
- Middleware belongs to the protocol when every handler/client must satisfy the concern. Do not hide application authorization in transport setup.

### Payload construction and request identity

Generated clients accept the payload value, for example `client.GetTurn({ turnId })`; they add the RPC tag and transport envelope. Do not manufacture `{ _tag: ... }` request envelopes or cast arbitrary payloads. When `primaryKey` is configured, `Rpc.make` internally turns struct fields into a payload class carrying that key (`.repos/effect/packages/effect/src/unstable/rpc/Rpc.ts:902-956`); callers still use the generated client contract.

RPC transport request IDs correlate one invocation and support acknowledgement/interruption. They are generated by the client and are not domain idempotency keys (`RpcClient.ts:264-283,365-422`). If a command can be retried or recovered, include a stable domain command/operation ID in its payload and enforce idempotency in the handler/storage transaction.

## Handlers and layers

Generate handlers from the same group instead of maintaining a second dispatch table. `RpcGroup` can turn implementations into handlers or layers, retaining each RPC's middleware and requirements (`.repos/effect/packages/effect/src/unstable/rpc/RpcGroup.ts:196-300`).

Keep handlers thin:

1. schema decoding establishes the transport value;
2. middleware establishes authenticated/authorized context;
3. the handler delegates to an application capability;
4. expected outcomes return declared success/error values;
5. unexpected failures remain defects and are observed at the boundary.

Never trust an internal transport as authorization. Authenticate peers, authorize the caller against the addressed resource, and propagate only the minimum safe context.

## Client lifetime and transport

`RpcClient.make(group)` is scoped: it installs a receive loop with `forkScoped`, tracks in-flight requests, compiles codecs per client, and removes entries on completion/interruption (`.repos/effect/packages/effect/src/unstable/rpc/RpcClient.ts:631-771`). Build it in a Layer or other owning scope, not per call.

For HTTP, `RpcClient.makeProtocolHttp(client)` adapts an existing policy-bearing `HttpClient`; therefore apply timeouts, SSRF policy, redirect policy, response bounds, authentication, and observability to that client before creating the RPC protocol (`RpcClient.ts:873-988`). Server and client must use compatible serialization layers.

Use `RpcClient.withHeaders` for request-scoped propagation such as an internal authorization token or safe correlation metadata. Header propagation is fiber-local and merged into outgoing calls (`RpcClient.ts:779-817`). Never put secrets into span attributes or logs.

## Serialization and bounds

Choose serialization as part of the transport contract:

- `layerJson`: whole messages only; the transport must frame them.
- `layerNdjson`: newline-framed streaming JSON.
- `layerMsgPack`: framed binary encoding with better binary support.
- `layerSchemaBinary`: framed schema-derived encoding; evaluate compatibility deliberately.

NDJSON and MessagePack retain incomplete frames and default to a 16 MiB maximum buffer. `layerMsgPackWith({ maxBufferSize })` and `layerNdjsonWith({ maxBufferSize })` let the application lower that bound; `"unbounded"` disables the protection (`.repos/effect/packages/effect/src/unstable/rpc/RpcSerialization.ts:82-103,118-159,522-571,677-713`).

Repository rule: always set an explicit, operation-appropriate bound for network transports. The serializer bound protects retained incomplete frames; it is not a substitute for HTTP body limits, decoded-schema limits, stream element limits, or business limits. Keep all of them.

MessagePack's `useRecords` and other `msgpackr` options are peer compatibility choices. Change them only on both sides and cover the exact production serialization in an adapter test.

## Errors, defects, and interruption

A client call can fail with:

- the RPC's declared error schema: an expected remote outcome;
- `RpcClientError`: transport, socket/worker/HTTP, or malformed/incompatible protocol failure;
- a defect/cause: an unexpected server or local schema/implementation failure.

`RpcClientError.reason` preserves the transport category, including `RpcClientDefect` for protocol/decoding failures (`.repos/effect/packages/effect/src/unstable/rpc/RpcClientError.ts:18-61`). Do not collapse these into a domain `NotFound`/`Unavailable` error. Retry only a specifically classified transport or declared transient error, and only when the operation is mutation-safe or idempotent.

Client interruption sends an RPC `Interrupt` message and clears local tracking. A disconnected or interrupted client therefore normally interrupts server work; do not infer durable completion from having sent the request (`RpcClient.ts:392-422,540-570`). For work that must survive callers, route the command through Cluster persistence, Workflow, or PersistedQueue and return an operation identity/status contract.

Streams require bounded consumption and explicit ownership just like ordinary Effect streams. Cancellation must close the scope and propagate interruption; do not fork a stream consumer outside the client scope.

## Cluster composition

`Entity.make(type, rpcs)` uses an RPC group as the addressed entity protocol (`.repos/effect/packages/effect/src/unstable/cluster/Entity.ts:452-488`). The RPC schema still defines wire values, while Cluster adds entity identity, placement, message persistence, and runner behavior.

- Annotate with `ClusterSchema.Persisted` only when message storage is configured; otherwise Cluster dies rather than silently pretending durability (`Sharding.ts:1098-1125`).
- `ClusterSchema.Uninterruptible` controls client/server interruption behavior; it does not make an operation transactionally idempotent (`ClusterSchema.ts:70-117`).
- Keep a stable domain operation ID in persisted mutation payloads. RPC request IDs and entity addresses do not replace it.
- Use authenticated Cluster transport and bounded MessagePack in production; see `.patterns/cluster.md` for topology, storage, and failover rules.

## Testing checklist

Test the protocol through its derived boundary, not only by calling handlers directly:

- payload, success, and declared-error schema round trips;
- the exact server/client serialization and options;
- malformed and oversized frames become protocol failure without unbounded retention;
- authentication/authorization and header propagation;
- interruption and disconnect behavior;
- stream cancellation/backpressure;
- duplicate delivery for persisted/idempotent commands;
- client/server version compatibility for any schema evolution.

Use in-memory transports for protocol semantics and at least one real HTTP/Cluster adapter test for framing, headers, limits, and lifecycle.
