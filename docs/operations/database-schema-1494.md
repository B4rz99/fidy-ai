# Final feature storage inventory (#1494)

This inventory describes the fresh-install baseline, not a claimed live deployment. The final
rollout checkpoint in [the cutover record](database-cutover-1428.md) records live convergence.

There are **109 application tables**. SQLite bookkeeping and the historical Alchemy migration
ledger are excluded. This is an inventory, not a fixed-count test or a target to optimize toward.
The previous 107-table design total did not include the accepted confirmed-upload writer record
and the independently added WhatsApp signup invitation. No generic workflow progress table or
application-owned operational observability store remains.

Every table has one persistence owner below. Foreign keys are storage constraints; logical User,
provider and workflow identities without a foreign key remain subject to owner authorization at
the action boundary. Shared stores are listed once. Dashboard has no dedicated tables: it uses
Transactions facts and its typed User Document. Workflows retain engine execution progress;
D1 retains domain intent, current authority, exact outcomes and external-effect reconciliation.

| Owner                                  | Why this set is separate                                                                                                             |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Identity (1)                           | Stable User, original trial and current identity facts                                                                               |
| Browser Login / WebSession (2)         | Independent short-lived proof and live browser authority                                                                             |
| Provider Authentication / Recovery (8) | Distinct provider/mailbox/recovery proofs, bounded attempts and one-use transitions                                                  |
| Tokens / OAuth Agents (7)              | Independent grants, credentials, public clients and exact operation approvals                                                        |
| Consent (3)                            | Append-only evidence, offered disclosure and pending authenticated response have different lifetimes                                 |
| Transactions (8)                       | Effective financial facts, immutable correction/selection evidence and bounded indexed aggregates                                    |
| Categories (2)                         | Shared taxonomy and independently editable per-User normalized rules                                                                 |
| Budgets (7)                            | Caps, month/group decisions, per-instant recomputation, grouped publication and original first-creation state                        |
| Ingestion (12)                         | Bounded admission, source material, review, per-record outcome and external-byte retention each have their own cardinality/lifecycle |
| Subscription (9)                       | Contract, authorization, provider settlement, prices, refund and cancellation retain separate identity and evidence                  |
| Quotas / Resource Admission (4)        | Commercial consumption is distinct from resource protection and atomic grant/refusal evidence                                        |
| Recurring / Recurring Planning (8)     | Detected patterns, editable plans, immutable revisions, exceptions, fulfillment and dispatch have independent cardinality            |
| Insights / Proactivity (10)            | Occurrences, reports, delivery intent, schedule evidence and per-User policy are distinct from engine execution progress             |
| Agent / Memory (6)                     | Session/Turn lifecycle, exact confirmations and visible transcript settle independently; Memory is explicit durable prose            |
| WhatsApp (5)                           | Verified channel evidence, current routing, provider authorization and uncertain delivery retain different lifecycles                |
| Connections (2)                        | Long-lived institution authorization and bounded per-attempt proof                                                                   |
| Audit (2)                              | Metadata-only accountability and narrowly scoped deletion authorization                                                              |
| Erasure (7)                            | Cross-owner deletion, confirmed upload drain, external cleanup and restoration fence need independent bounded records                |
| User Documents (1)                     | Single persistence owner for typed feature documents; consumers retain domain policy                                                 |
| Canonical Admission / Atomic Unit (5)  | Atomic child fence, pacing, live lease, exact replay and transaction assertion each enforce a distinct boundary                      |

## Conditional design outcomes

- Recipient routing is the approved five-column `whatsapp_recipients` table; login identity stays
  in `users`. Connection availability comes from code registration, with no institution-gate table.
- Confirmed uploads retain `erasure_writers` until settlement, preventing a late upload from
  recreating deleted bytes. Erasure keeps only necessary restoration/custody metadata; it does not
  archive deleted User content. Bounded direct deletion requires no selection/chunk helper table.
- Operational alerts, counters and health snapshots use native platform observations and monitors.
  Five custom monitor slots require one combined owner-attention stream rather than independent
  per-owner notification/cooldown state. The runbook records this coverage difference explicitly.
- `sql_assertions` remains one shared atomic assertion store; obsolete per-feature assertion tables
  and custom migration status tables are absent. Exact financial and authorization evidence is
  retained even where it resembles operational progress.
- The single fresh baseline includes the signup invitation introduced independently on trunk.
  Existing databases retain both historical migration receipts; consolidation never reruns the
  baseline or erases the migration ledger.
