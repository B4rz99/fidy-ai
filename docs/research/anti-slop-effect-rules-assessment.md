# Anti-slop Effect rules against Fidy's patterns

Snapshot: [`dmmulroy/anti-slop@c44ef22`](https://github.com/dmmulroy/anti-slop/tree/c44ef22ca116d0ba62a3ff663a0bd13a3f3fa40b/src/effect/rules). This is an adoption assessment, not an enabled gate. The five rules and their opt-in config are listed in [the upstream README](https://github.com/dmmulroy/anti-slop/blob/c44ef22ca116d0ba62a3ff663a0bd13a3f3fa40b/README.md#L78-L105). The upstream package is `private` and targets Oxlint and `@oxlint/plugins` 1.78.0 ([package.json](https://github.com/dmmulroy/anti-slop/blob/c44ef22ca116d0ba62a3ff663a0bd13a3f3fa40b/package.json#L1-L30)); Fidy uses Oxlint 1.83.0 and an existing JS plugin ([package.json](../../package.json), [`.oxlintrc.json`](../../.oxlintrc.json#L1-L10)). Its plugin loaded successfully for the one-off probe below, but that is **not** a support or packaging guarantee.

## Measured scope

A throwaway Oxlint config enabled just the five upstream Effect rules with the upstream TypeScript plugin loaded from a temporary checkout; the installed Fidy Oxlint binary checked `apps/server/src`, `apps/server/cloudflare`, `apps/web/src`, `apps/web/e2e`, `infra/cloudflare`, `scripts`, and `tools`. Plugin-labelled diagnostics (including tests) were **2** `no-manual-effect-error-tag`, **289** `no-manual-tag-comparison`, **627** `no-manual-tagged-construction`, **16** `no-service-constructor-imports`, and **0** `prefer-effect-match` (934 total). These are _syntactic diagnostics_, **not 934 bugs**. Reproduce by cloning the pinned commit, installing its `@oxlint/plugins@1.78.0` dependency in the temporary checkout, and running Fidy's `oxlint --config <temporary config with jsPlugins [{ name: "anti-slop-effect", specifier: "<clone>/src/effect/index.ts" }] and the five rules set to "error">` on the listed directories. The [rule registration](https://github.com/dmmulroy/anti-slop/blob/c44ef22ca116d0ba62a3ff663a0bd13a3f3fa40b/src/effect/index.ts#L1-L23) fixes the names used here. This probe changed no Fidy configuration or app source.

## Keep linted rules out of `CODING_STANDARDS.md`

The standards are for decisions that a lint error cannot supply. The accompanying [documentation cleanup](../../CODING_STANDARDS.md) removes prose that repeats active checks: ordinary interface declarations, assertion/cast syntax, `Effect.promise`, `useEffect`, core open dictionaries and explicit `unknown` parameters, exported-core comment presence, and nullable/optional **type** examples. The global rules are in [`.oxlintrc.json:34–41`](../../.oxlintrc.json#L34-L41) and [`.oxlintrc.json:108–119`](../../.oxlintrc.json#L108-L119); core-only rules are in [`.oxlintrc.json:324–340`](../../.oxlintrc.json#L324-L340). The handwritten-symbol check was extended to server, Worker, browser, and infrastructure production source before removing its broad prose prohibition ([guard](../../apps/server/scripts/check-lint-guards.ts#L7-L30)). It does not scan every repository tool or test fixture; do not claim coverage outside the listed trees. The emitted diagnostics now carry the removed remediation: closed aliases and the reviewed augmentation, validated scalar brands and closure-backed capabilities, correlated optional fields as unions, typed Promise rejection, and justified React integration exceptions ([plugin messages](../../scripts/oxlint/effect-guards.js); [symbol guard](../../apps/server/scripts/check-lint-guards.ts)). The nullable diagnostic uses Effect v4's `Schema.OptionFromNullOr` for present nullable fields rather than the removed `Schema.optionalWith` API. Valid `as const` inference and runtime absence guidance remain in the standards because neither produces a lint error.

The remaining [services-versus-functions rule](../../CODING_STANDARDS.md#services-vs-plain-functions), [errors and absence decisions](../../CODING_STANDARDS.md#errors-and-absence), [foreign-Promise error classification and interruption](../../CODING_STANDARDS.md#promise-interop), and [React state ownership](../../CODING_STANDARDS.md#react) are not established by these syntax guards. They must remain in review. The prior class paragraph claiming no linter could draw any distinction was also removed: [the earlier feasibility study](./ast-standards-feasibility.md#candidate-2--extending-a-first-party-class) established that a type-aware check can identify a subset of first-party inheritance, not class purpose.

## Recommendation

Do **not** install the full plugin. Keep the standards cleanup separate from any decision to adopt these rules: none of the five is currently justified as a mandatory repo-wide gate. If a two-site refactor is desired, test `Effect.catchReason` at both HTTP seams independently of the upstream diagnostic; do not enable `no-manual-effect-error-tag` as-is without distinguishing `catchIf`'s predicate from its recovery handler.
