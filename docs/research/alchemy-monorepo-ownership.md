# Alchemy in Fidy's monorepo — source-backed architecture assessment

Research date: 2026-09-20. This document records the pre-migration layout; links to moved runtime files under `infra/cloudflare/` refer to their current counterparts under `apps/server/cloudflare/`. This is an assessment, not a migration plan or a change to the adopted architecture. Alchemy's current website can evolve independently of Fidy's pinned `alchemy@2.0.0-beta.79`; verify a proposed API against `.repos/alchemy` and the installed package before changing code.

## How Alchemy works

- `Alchemy.Stack(name, { providers, state }, Effect)` is the deployment unit. Providers perform resource operations; state persists the last deployed input/output for a stack and stage; the returned value is the stack's output. The Effect declares resources with stable logical IDs and their dependency graph. [Stacks](https://alchemy.run/infrastructure-as-code/stack/), [State store](https://alchemy.run/state-store/).
- A plan compares declarations with persisted state; deploy reconciles creates/updates/replacements/deletions; undeclared resources are candidates for deletion. `alchemy plan` applies nothing, `alchemy dev` watches and reconciles locally, and `destroy` removes the stack in dependency order subject to removal policies. Changing a logical ID is not a harmless file move: it can replace a resource. See [Resource lifecycle](https://alchemy.run/infrastructure-as-code/resource-lifecycle/) and [Renaming](https://alchemy.run/infrastructure-as-code/renaming/). An _unchanged_ resource declaration moved to a different source file need not change the logical ID, but must be plan-checked.
- `Output`s express deploy-time dependencies: yielding a Worker then using its URL in a web resource wires their order within one stack. Separate stacks instead read previously persisted typed outputs at plan time and require deployment/destroy ordering. [Single-stack walkthrough](https://alchemy.run/project-structure/monorepo-single-stack/), [Multiple stacks](https://alchemy.run/project-structure/monorepo-multi-stack/), [References](https://alchemy.run/infrastructure-as-code/references/).
- Do not confuse a Cloudflare Worker runtime with the plan: an Alchemy-native Worker can return an Effect-backed request handler from a construction Effect; the construction phase runs at planning and cold start and the handler at request time. Fidy currently uses a separate Worker entrypoint `main` and plain Cloudflare `fetch` entry instead, which Alchemy supports; adopting the newer co-located Worker idiom is optional, not a prerequisite for putting application code near its owner. [Phases](https://alchemy.run/infrastructure-as-effects/phases/), [single-stack example in pinned checkout](../../.repos/alchemy/examples/monorepo-single-stack/backend/src/Service.ts), [Fidy stack](../../infra/cloudflare/alchemy.run.ts), [Core Worker](../../infra/cloudflare/core-worker.ts).

## What the project-structure docs actually recommend

- [Monorepo](https://alchemy.run/project-structure/monorepo/) recommends starting with **one stack**, even with frontend and backend packages. Multiple stacks are for genuinely independent deployment/destroy cadences or additional backend consumers; they introduce typed cross-stack references and ordering. One stack does **not** require one `infra/` package: [Single Stack](https://alchemy.run/project-structure/monorepo-single-stack/) places the stack at root and a Worker declaration/entrypoint in the backend package. Importing that declaration into the root stack creates no separate state or deploy.
- [File layout](https://alchemy.run/project-structure/file-layout/) says to start in one file, split when it grows, group resources that share a lifecycle, and keep `alchemy.run.ts` the composition root. A resource declaration is inert until the stack yields it. This is guidance about **ownership and composition**, not an order to create one file for each tiny binding or to wrap every D1 adapter in an Alchemy Layer. Where a Worker declaration is in a different package, anchor `main` with `import.meta.url` or `new URL(..., import.meta.url).href`; don't rely on shell cwd. [Single Stack, Anchor every path](https://alchemy.run/project-structure/monorepo-single-stack/#anchor-every-path).
- The [Layers](https://alchemy.run/infrastructure-as-effects/layers/) pattern is for an actual reusable/substitutable capability with bindings. It is not required merely because a file imports `effect`.

## Executor is a different reference, not an Alchemy template

At inspected revision [`9e143d9`](https://github.com/UsefulSoftwareCo/executor/tree/9e143d99c28f4c26d9e2cb1b136658048fecd3cb), Executor does **not** deploy its Cloudflare host with Alchemy. Its [`apps/host-cloudflare/README.md`](https://github.com/UsefulSoftwareCo/executor/blob/9e143d99c28f4c26d9e2cb1b136658048fecd3cb/apps/host-cloudflare/README.md) describes one self-hosted Cloudflare Worker assembled from reusable packages. [`package.json`](https://github.com/UsefulSoftwareCo/executor/blob/9e143d99c28f4c26d9e2cb1b136658048fecd3cb/apps/host-cloudflare/package.json) runs `wrangler deploy`; [`wrangler.jsonc`](https://github.com/UsefulSoftwareCo/executor/blob/9e143d99c28f4c26d9e2cb1b136658048fecd3cb/apps/host-cloudflare/wrangler.jsonc) declares its Worker/assets/D1/R2/DO bindings. The codebase only mentions Alchemy incidentally ([repository search](https://github.com/UsefulSoftwareCo/executor/search?q=alchemy&type=code)). **Inference:** its transferable lesson is that Cloudflare runtime ownership can sit with a host application, not how to structure Alchemy stacks. Do not copy its auth, deployment authority, or process-local MCP session choices into Fidy.

## Fidy assessment and proposed seam

Fidy currently has **one** production stack at [`infra/cloudflare/alchemy.run.ts`](../../infra/cloudflare/alchemy.run.ts), with Cloudflare state for remote production and local state in `alchemy dev` ([configuration](../../infra/cloudflare/deployment-configuration.ts)). Its [root architecture](../../ARCHITECTURE.md), [server architecture](../../apps/server/ARCHITECTURE.md), and [web architecture](../../apps/web/ARCHITECTURE.md) explicitly give `@fidy/cloudflare-infra` the topology and Worker entrypoints, while the server owns domain/contract and web owns browser/static artifact. This is a _local architectural choice_, not an Alchemy requirement. The current `infra/cloudflare` contains not only stack wiring and edge policy but onboarding, browser login, PAT, billing, transactions, document Workers and their tests ([directory](../../infra/cloudflare/)); most are application runtime adapters. This creates the growing-files and ownership concern independently of stack count.

**Recommended direction (proposal):** retain one stack, the current logical IDs, state backend, ingress→Core privacy graph, D1 migrations and release gates. Move server-specific Worker entrypoints, D1/DO/Queue/Workflow adapters and adjacent tests toward `apps/server/cloudflare/` (or a clearly named server-owned adapter subtree); keep server's portable `core/` and `shell/` free of platform imports. Keep web-owned artifact/build/header checks with `apps/web/`; its production site remains assets-only. Leave genuinely cross-app _deployment_ topology (domains, WAF, shared resource declarations, state, stack outputs) in a small root `infra/cloudflare/` or root composition module. The single stack may import declarations from application packages. Decide separately where D1 migrations live: they are server-owned schema changes, but the stack must continue pointing at their single authoritative directory. Do not move security admission to ingress merely to reduce file count.

Alternative: move the single `alchemy.run.ts` to repo root as in the docs. This is a layout change, not a second stack; check anchored paths, workspace TypeScript dependency direction, scripts, CI, and the complete plan first. Splitting web/server into independently deployable stacks would add persisted cross-stack references and conflicts with the current one-revision coordinated release and service-binding topology; it needs a _deployment_ requirement, not just directory tidiness. [Fidy architecture](../../ARCHITECTURE.md), [monorepo chooser](https://alchemy.run/project-structure/monorepo/).

Migration safety: first inventory Alchemy logical IDs and physical names; move one cohesive runtime feature with its tests at a time; adjust import paths and narrowly relocate declarations, if any; verify `tsc`, local service-binding/D1 tests, artifact policy, `alchemy plan --stage production` with proper CI credentials, and the plan's explicit no-delete/no-replace expectations for existing resources. Production state and resources are not throwaway, even though product API backwards compatibility is unnecessary. [Lifecycle](https://alchemy.run/infrastructure-as-code/resource-lifecycle/), [Fidy stack](../../infra/cloudflare/alchemy.run.ts).

## About `async` and “disabling the linter”

- This is primarily an **Effect language-service diagnostic**, not the oxlint directive. The global `asyncFunction: error` is in [`tsconfig.base.json`](../../tsconfig.base.json); it has specific path overrides (web tooling/tests etc.) but not a blanket infra exception. Many infra files individually use `// @effect-diagnostics-next-line asyncFunction:off` (e.g. [`verified-onboarding.ts`](../../infra/cloudflare/verified-onboarding.ts), [`transaction-boundary.ts`](../../infra/cloudflare/transaction-boundary.ts)). [`scripts/check-lint-suppressions.ts`](../../scripts/check-lint-suppressions.ts) bans oxlint/eslint suppression strings, **not** Effect diagnostic directives. These are real per-declaration opt-outs from a repository gate, not an Alchemy convention.
- A Cloudflare `fetch` handler must ultimately return `Promise<Response>`; that does **not** require its body or its D1 adapters to use `async`. [`core-worker.ts`](../../infra/cloudflare/core-worker.ts) and [`public-worker.ts`](../../infra/cloudflare/public-worker.ts) show `Effect.runPromise` at the Worker edge; [`transaction-boundary.ts`](../../infra/cloudflare/transaction-boundary.ts) shows both a suppressed async D1 function and an `Effect.tryPromise` counterpart. [Fidy Promise standard](../../CODING_STANDARDS.md#promise-interop) starts foreign rejectable Promises with `Effect.tryPromise` and classifies failures; it does not endorse turning every internal workflow into async or `Effect.promise`.
- **Conclusion:** no general Alchemy/Cloudflare rule justifies automatically adding `asyncFunction:off`, `missingPipeableSignature:off`, or global overrides. If a narrow foreign callback or test harness genuinely requires native async, document why at the owning adapter and make the exception explicit and reviewable; otherwise keep Effect work in Effect and convert only at the external Promise boundary. Consider a separate gate or reviewed allowlist for `@effect-diagnostics-*` directives, since the current anti-suppression script does not cover them. Do not silently change the diagnostics to green a PR.

## Open questions before implementation

1. Should server own D1 migrations and durable admission policy, or should a small deployment-owned subtree retain the D1 schema while app adapters move? Avoid two schema authorities.
2. Must `infra/cloudflare` remain a workspace package for Alchemy dependencies, or is root composition preferable? This is packaging; it does not determine number of stacks.
3. Which `asyncFunction` exceptions are truly imposed by foreign APIs, and which are just convenient adapters that should be converted? Audit them feature by feature, not with a bulk rewrite.
