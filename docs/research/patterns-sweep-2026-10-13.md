## Coverage and method

Work was split between server, web, CLI plus server core/Dashboard/documents, and root scripts/infrastructure owners. Owners inventoried files, searched for native Promise/resource APIs, whole-body collection, Schema boundaries, interruption handling, concurrency, retries, authority and telemetry, then manually traced relevant risk boundaries. Changed transport and cancellation code also received an independent review.

The [coverage evidence](patterns-sweep-2026-10-13.coverage.json) preserves owner inventories, named manual traces, findings and reported checks. Its preserved inventory snapshot at `b9ede142a` includes 994 tracked implementation files under `apps`, `scripts`, `infra` and `tools`: 23 CLI, 708 server, 181 web, 44 scripts, 34 infrastructure and four tools. It deliberately includes SQL, shell/PowerShell, Python, CSS/HTML and executable configuration, separates supporting tests/fixtures and generated files, and excludes upstream repositories, dependencies, agent skills and non-code assets.

The evidence records 1,263 snapshot code/support paths represented by owner systematic scans and 178 named manual paths. These counts overlap and include supporting files; they must not be summed or treated as production coverage percentages. A pattern scan is a search for named shapes, not a semantic review. Manual paths were traced at named behavior seams, not necessarily every line.

An initial reconciliation found unnamed implementation paths, mostly static SQL, shell, Python, tools and executable configuration. A supplemental scan read those files for applicable SQL/security constraints, foreign parsing, process/HTTP resource lifetimes, output retention and secret projection. Suspicious process owners and fresh trunk provider-admission code received manual traces. All 994 tracked implementation paths in that snapshot now have named systematic scan evidence; no unrepresented implementation paths remain in this inventory. Static DDL does not run Effect cancellation, and a shape scan does not prove every historical migration's domain behavior. The JSON separates supplemental scans from root-reported manual tracing.

Historical inventories are filtered against existing tracked files after rebase, so removed jsdom suites do not count as current coverage. New implementation/test files introduced after that inventory snapshot are listed separately. Fresh provider admission was traced through ingress header replacement, durable source/global budgets and private proof polling; no new security finding was identified.

The latest security rebase added five implementation paths beyond that snapshot: one SQL migration, the server session binding boundary, and three browser authentication/session binding modules. Independent compatibility traces cover the new runtime paths; root review covers the SQL constraints and combined edge policy. The evidence lists these paths separately.

## Verified library caveat

In installed Effect 4.0.1, `HttpClientResponse.stream` uses `Stream.fromReadableStream`, which delegates to `Channel.fromReadableStream`. The private `readableStreamToPullUnsafe` finalizer defaults to awaiting `reader.cancel().catch(...)` and does not release the reader lock. `releaseLockOnEnd: true` chooses lock release instead of cancellation; it does not stop underlying work. These exact branches were checked in `node_modules/effect/src/Channel.ts`, `Stream.ts` and `http/HttpClientResponse.ts`; `http/FetchHttpClient.ts` supplies the request AbortSignal to native fetch.

The [HTTP pattern](../../.patterns/http-client.md) and [stream pattern](../../.patterns/streams.md) now explain why a byte cap or timeout alone does not prove cleanup settles, link the native Fetch owners, and distinguish the MCP SDK lease settlement guarantee. Tests must exercise native adapters with pending/rejected cancellation and malformed chunks; an ordinary stub HttpClient cannot prove this behavior.
