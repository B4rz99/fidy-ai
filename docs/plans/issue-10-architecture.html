Review artifact · GitHub issue #10

Kapso → consent → one safe, serialized turn

A concrete WhatsApp adapter that authenticates Kapso deliveries, composes the implemented consent gate, durably collapses already-authorized bursts, invokes AgentService.handleTurn once, and enforces free-form delivery under current consent, RLS, and the 24-hour window.

Approved — production implementation completed Issue #8 consent merged Issue #81 RLS merged 2.5 s quiet period Durable inbound job queue No generic channel framework

Landed foundations this plan now uses

shell/consent/consent-gate.ts

Prefactor the existing conversation boundary into admission and execution. Admission reuses evaluateConsentGate, validates one real provider message, and returns either a terminal consent outcome or an authorized InboundMessage. Only the authorized result carries a stable UserId that may be queued.

core/_shared/provider-message-evidence.ts

Reuse ProviderMessageEvidence with concrete whatsapp/kapso qualifiers. Disclosure and decision evidence remains owned by Consent rather than being duplicated in channel tables.

core/identity/reference.ts · shell/identity/repo.ts

Reuse UserId, E164PhoneNumber, and the narrow fidy_resolve_whatsapp_user gateway behind resolveWhatsAppCaller. Add only the owner-published read needed to find a User's current WhatsAppIdentity before outbound delivery.

shell/db/user-transaction.ts · ADR-0007

All four new User-owned tables use forced RLS and withUserTransaction. A new deny-by-default claim function returns only an opaque claim id and stable UserId; queue content is loaded later under that User's context.

shell/consent/repo.ts · ADR-0008

Queue acceptance and outbound projection run inside short useCurrentConsent units serialized with revocation. The transaction ends before any model or Kapso network call begins.

shell/agent/agent-service.ts

Reuse InboundMessage, AgentReply, and AgentService.handleTurn. The existing AgentService independently rechecks current consent around Transcript, token, and canonical-operation work.

Admission versus execution: today handleAgentConversationTurn admits one message and immediately executes one AgentService turn. Extracting admitAgentConversationTurn lets the existing function keep that behavior while WhatsApp admits each real WAMID, pauses for debounce, and executes once with the collapsed burst. Consent is never evaluated against a synthetic multi-message WAMID.

What changes, at a glance

1

Authenticate and bound

Bound raw bytes, verify X-Webhook-Signature with HMAC-SHA256 and a timing-safe comparison, then decode. Invalid proof causes zero writes or sends.

2

Claim receipt, then evaluate consent

Claim each authenticated WAMID before any consent side effect, apply durable phone/User ingress budgets, then project text or voice transcript into ConsentGateInput. Consent outcomes reply immediately; acceptance itself never becomes financial processing.

3

Durably admit Proceed

Under the resolved User's RLS and current-consent lock, atomically retain attributable evidence, enqueue transient content, and extend windowOpenUntil. Complete the receipt claim before acknowledging.

4

Claim identity, then content

After 2.5 seconds of quiet, the narrow gateway claims one due User and returns no content. The worker loads the ordered burst in a separate User-scoped transaction.

5

Serialize in Postgres

Claim state permits one active turn per User across worker fibers and application instances while different Users proceed concurrently. No lock spans network work.

6

Authorize exact egress

In one short transaction, recheck consent, current WhatsAppIdentity, and the window, then send the exact text through Kapso only after that transaction commits.

Only kapso-webhook.ts, kapso-client.ts, and Kapso configuration are replaced if WhatsApp moves to another provider; they project through the WhatsApp-owned model before persistence. This is a concrete seam, not a provider registry.

Implemented interface constraints

Canonical declarations live under src/shell/channels/whatsapp; docs/plans/issue-10-proposed-types.ts now links to those production sources. Their key constraints are:

AgentConversationAdmission

Consent outcomes or AuthorizedTurn; only the latter carries the admitted UserId and InboundMessage into WhatsApp persistence.

KapsoMessageEvidence

Refines the existing provider-qualified evidence to WhatsApp/Kapso. WAMID remains evidence, never identity or authority.

WhatsAppTurnClaim

Exactly claimId + UserId. The cross-User gateway cannot return message content.

startWhatsAppTurn result

One WhatsAppTurnClaim, one stable User, an ordered non-empty message list, and one bounded InboundMessage.

WhatsAppWindowState

Open | Closed; absence cannot accidentally authorize free-form send.

KapsoClient

Narrow true-external service for validated text send and decoded provider evidence; internal orchestration remains plain functions.

Implemented slices

  1. Authenticated route: failing recorded-payload tests → bounded raw-body verification and v2 decoding with zero invalid-proof effects.
  2. Consent delivery: unknown, awaiting-delivery, accept, decline, clarify, and terminal acceptance behavior through the real Consent gate and Kapso client.
  3. Authorized durable admission: migration 0012, receipt replay guard, ingress budgets, RLS policies, and the current-consent evidence/enqueue/window transaction.
  4. Claim and burst: narrow claim gateway, unstarted lease, ordered bounded collapse, database-enforced per-User serialization, and one AgentService call.
  5. Voice: transcribed audio follows consent and the same authorized queue; absent/empty/oversized transcript fails before persistence or model work.
  6. Outbound: exact reply projection under current consent, current WhatsAppIdentity, and window; provider call outside the transaction; metadata cleanup.
  7. Isolation and assembly: two-User background guard, real application and harness layers, retention/failure startup handling, and configuration.
  8. Verification: focused checks throughout, full repository verification, and security-aware code review before merge.

Decisions for review

Consent ordering: evaluate every provider event before debounce. Send terminal consent text immediately; queue only Proceed. An Accepted turn never replays the financial request that originally began onboarding—the User sends it again, matching issue #8's implemented contract.
Consent delivery is at least once: no database transaction can include a Kapso call. A timeout or crash after Kapso accepts a disclosure but before Fidy records its WAMID can resend that same disclosure. The gate still prevents acceptance until one authoritative delivery is recorded, and no duplicate financial turn can result.
RLS queue authority: use a fixed claim gateway that returns only claim id and UserId. Enforce one active claim per User in Postgres rather than relying on one process's in-memory active-User set.
Do not replay ambiguous started work: suppose a worker marks a burst Started, quick-log commits a Transaction, and the process crashes before it marks the claim complete. On restart, the queue cannot prove whether zero or several canonical effects committed. Automatic replay could create a duplicate Transaction or duplicate WhatsApp reply, so started work becomes failed metadata and the User may resend. A claim that expires before Started is safe to reclaim because the contract guarantees that no AgentService or provider call began. The cost is that a crash between marking Started and the first effect can lose one turn; exactly-once recovery would require an idempotency key propagated through AgentService and every canonical mutation.
Resource-bound provenance:
  • 100 events is Kapso's documented maximum configurable buffered batch size.
  • 16,000 collapsed characters is Fidy's existing TranscriptText maximum; an oversized burst is rejected whole rather than truncated or partly processed.
  • 1 MiB raw body remains a provisional Fidy memory/CPU guard because Kapso documents no byte limit. Production payload telemetry must validate it before the bound is raised.
  • 32 messages per burst is a provisional anti-abuse/cardinality guard; excess rejects the whole burst with a retry-smaller response.
  • 30-second receipt and unstarted-turn leases are provisional internal crash-recovery allowances; neither lease keeps a database transaction open across external work.
  • Eight concurrent Users is a provisional provider/model/connection spend cap, to be configurable and verified against the runtime pool.
Only the 100-event and 16,000-character values currently have external or repository contract sources; the other exact defaults remain review choices.

Explicitly out of scope

No plugin base, provider selector, generic identity, or runtime channel router.
