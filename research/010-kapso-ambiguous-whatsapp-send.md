# Research 010: Can Fidy reconcile an ambiguous Kapso WhatsApp send?

- **Question:** If Fidy loses the HTTP response from a Kapso send, can it reliably discover whether that exact attempt was sent, without sending it again?
- **Sources consulted:** Kapso's public send, message retrieval/listing, and webhook documentation (links below); Fidy's existing adapter and state transitions. This is an analysis of documented guarantees, not a live provider test.

## Findings

1. **A successful send returns a WhatsApp message ID (`wamid`), but the send contract does not document a client-supplied idempotency key.** It accepts `biz_opaque_callback_data`, described as an arbitrary tracking string echoed in webhooks, not as send deduplication. [Kapso, **Send a message**, request fields and response](https://docs.kapso.ai/api/meta/whatsapp/messages/send-a-message).
2. **Kapso documents a get-message interface by message ID and list-message interfaces.** The documented message projections include delivery status and status history. If Fidy persisted the message ID from a successful response, it can investigate that message; if the response was lost before recording its ID, get-by-ID alone cannot find the attempt. The public list contracts do not document a correlation-token (`biz_opaque_callback_data`) lookup or an exact-send search guarantee. A bounded list query may supply clues but cannot prove an absent send or justify resending. [Kapso, **Get message**](https://docs.kapso.ai/api/platform/v1/messages/get-message); [Kapso, **List messages**](https://docs.kapso.ai/api/platform/v1/messages/list-messages); [Kapso, **Meta-compatible list messages**](https://docs.kapso.ai/api/meta/whatsapp/messages/list-messages).
3. **Kapso documents outbound `sent`, `delivered`, and `failed` webhook events, and recommends deduplicating webhook deliveries with `X-Idempotency-Key`, not message ID (which is shared by multiple statuses).** The opaque callback field is promised to be echoed in webhooks by the send contract. Webhook delivery is not guaranteed forever: after configured attempts fail, Kapso marks delivery failed, and it may pause a failing webhook. Therefore absence of a callback is not proof that a send did not happen. [Kapso, **Message events**, events and deduplication](https://docs.kapso.ai/docs/platform/webhooks/message-events); [Kapso, **Webhook delivery**, retry policy and automatic pausing](https://docs.kapso.ai/docs/platform/webhooks/advanced); [Kapso, **Send a message**, `biz_opaque_callback_data`](https://docs.kapso.ai/api/meta/whatsapp/messages/send-a-message).
4. **The current Fidy adapter distinguishes definite rejection from ambiguous transport/timeout/5xx and does not automatically retry ambiguous outcomes.** Its send payload includes an opaque callback token. [apps/server/src/shell/channels/whatsapp/kapso-client.ts](../apps/server/src/shell/channels/whatsapp/kapso-client.ts) (types `KapsoSendFailed`, `KapsoClientService`; `classifyHttpStatus`, `encodeTextMessage`). Disclosure currently requires `disclosure_message_id` equal to the callback message ID, so a lost response can leave an authentic callback unable to advance the exchange. [apps/server/cloudflare/onboarding/consent-ingress.ts](../apps/server/cloudflare/onboarding/consent-ingress.ts) (`sendExchange`, `recordDelivery`); [apps/server/cloudflare/migrations/0003_pending_consent.sql](../apps/server/cloudflare/migrations/0003_pending_consent.sql) (`pending_consent_delivery_requires_attempt`).

## Conclusion / safe implementation rule

**No reliable exact-attempt lookup by correlation token or outbound idempotency guarantee was found in the published contract.** Preserve one durable, unique attempt and its correlation token _before_ the provider call. Resolve it using an authenticated matching callback, or—when a `wamid` was recorded—an authenticated, bounded get-by-ID observation. Do not interpret missing callbacks, missing list results, or an expired timeout as definite non-delivery. Leave the attempt **unconfirmed** and do not blindly resend. A callback received before the HTTP response is stored must be reconcilable against the pre-persisted attempt; its proof must still be checked against phone number, correlation token, message ID, and valid timing.

## Unresolved provider proof

Ask Kapso whether a supported exact lookup by `biz_opaque_callback_data` or an outbound idempotency key exists, including retention, consistency, authorization, and behavior after a network timeout. Until an executable provider contract test verifies those guarantees, do not depend on them. Likewise verify the exact webhook payload path of the echoed token in a provider-shaped test fixture before changing the decoder.
